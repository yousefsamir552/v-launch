# نظام إدارة المصنع المتكامل (Factory ERP) - Full-Stack (React + Django REST API)

نظام متكامل لإدارة وتتبع خطوط إنتاج مصانع الملابس الجاهزة، يعمل بهندسة **Full-Stack حقيقية** تربط واجهة المستخدم (**React 19 + TypeScript + Vite + Tailwind CSS v4**) بخادم الباك إند وقاعدة البيانات المركزية (**Django + Django REST Framework + SQLite/PostgreSQL**).

---

## ما تم إصلاحه هندسياً في هذا الإصدار:

1. **إلغاء الدخول التلقائي بحساب الإدارة (Sudo / Admin)**:
   - تم إزالة الكود الذي كان يجبر المتصفح على الدخول بحساب `sudo` تلقائياً عند فتح الموقع لأول مرة أو من متصفح آخر.
   - الآن يفتح الموقع دائماً على **شاشة تسجيل الدخول** حتى يقوم المستخدم بإدخال اسم مستخدم وكلمة مرور صحيحة يتم التحقق منها عبر الباك إند (`/api/auth/login/`).

2. **إلغاء الاعتماد على التخزين المحلي للمتصفح (`localStorage`) كبديل لقاعدة البيانات**:
   - في السابق كانت جميع عمليات إضافة/حذف الحسابات والموديلات والخامات تتم داخل ذاكرة المتصفح فقط (`localStorage`) ولا تُرسل للباك إند، مما كان يجعل أي حساب تحذفه أو تنشئه يظهر في متصفحك فقط ولا يظهر عند فتح الموقع من جهاز أو حساب آخر.
   - تم تنظيف `AppContext.tsx` بالكامل من البيانات الوهمية المحفوظة محلياً، وأصبحت جميع القراءات والكتابات (إضافة/تعديل/حذف المستخدمين، الأدوار، الأقمشة، الألوان، الإكسسوارات، الموديلات، القص، الفرز، المطابع، المكن، الرسائل، وسجل المراقبة) تتم مباشرة في قاعدة بيانات الباك إند.

3. **نظام مصادقة وجلسات حقيقي في الباك إند (`AuthViewSet`)**:
   - تشفير كلمات المرور في قاعدة البيانات باستخدام `make_password` و `check_password`.
   - توليد رمز جلسة آمن (`auth_token`) عند تسجيل الدخول والتحقق من صلاحية الجلسة وحالة الحساب (`is_active`) عبر `/api/auth/me/`.
   - تهيئة الحساب الرئيسي (`sudo` / كلمة المرور الافتراضية: `14596357`) والأدوار الأساسية **مرة واحدة فقط** عند إنشاء قاعدة البيانات لأول مرة (`SystemSetting: initial_seed_v1`)، بحيث لا تعود الحسابات أو البيانات المحذوفة للظهور مرة أخرى.

4. **توحيد هيكل البيانات (Schema Parity) بين الفرونت إند والباك إند**:
   - تحديث `backend/api/models.py` و `backend/api/serializers.py` و `backend/api/views.py` وملف الترحيل `0002_full_erp_sync.py` لتطابق جميع الحقول والعمليات في واجهة React بنسبة 100%.

## طريقة التشغيل المحلي (Local Development):

### 1. تشغيل الباك إند (Django Backend):
افتح نافذة Terminal في مجلد `backend`:
```bash
cd backend
pip install -r requirements.txt
python manage.py migrate
python manage.py runserver 0.0.0.0:8000
```

### 2. تشغيل الفرونت إند (React + Vite Frontend):
افتح نافذة Terminal ثانية في المجلد الرئيسي للمشروع:
```bash
npm install
npm run dev
```
ثم افتح المتصفح على الرابط: `http://localhost:3000`

## متغيرات البيئة المطلوبة في الإنتاج (Render + Neon + Vercel):

| المتغير | الوصف | مثال |
| --- | --- | --- |
| `SECRET_KEY` | مفتاح Django السري (إلزامي عند `DEBUG=False`) | سلسلة عشوائية طويلة |
| `DEBUG` | يجب أن تكون `False` في الإنتاج | `False` |
| `DATABASE_URL` | رابط قاعدة بيانات Neon/PostgreSQL | `postgres://...` |
| `ALLOWED_HOSTS` | النطاقات المسموح بها (مفصولة بفواصل) | `erb-v-4-new.onrender.com` |
| `CORS_ALLOWED_ORIGINS` | أصل الواجهة الأمامية على Vercel | `https://your-app.vercel.app` |
| `SECURE_SSL_REDIRECT` | (اختياري) إجبار HTTPS داخل Django | `True` |

> **ملاحظة أمنية:** التطبيق يفشل في الإقلاع (fail-closed) إذا لم يُضبط `SECRET_KEY` مع تعطيل `DEBUG`.
> كما أصبحت جميع مسارات الـ API تتطلب ترويسة `Authorization: Bearer <token>` باستثناء `/api/auth/login/`،
> وأصبحت عمليات الكتابة في كل قسم تتطلب صلاحية ذلك القسم (مخزن القماش/الإكسسوارات/التصميم/القص/الفرز/المطابع/المكن).

## تخزين الصور على Cloudflare R2 (مطلوب لتشغيل رفع الصور):

كانت الصور تُخزَّن كـ Base64 داخل PostgreSQL، مما يستهلك باقة النطاق الترددي لقاعدة بيانات Neon مع كل مزامنة `/api/state/`.
الآن تُرفع الصور إلى Bucket على Cloudflare R2 ويُحفظ **الرابط العام فقط** في قاعدة البيانات (بدون أي تغيير في مخطط الجداول).

### 1) إنشاء الـ Bucket وضبط المتغيرات

| المتغير | الوصف |
| --- | --- |
| `R2_ACCOUNT_ID` | معرّف حساب Cloudflare (Account ID) |
| `R2_ACCESS_KEY_ID` | مفتاح الوصول من R2 API Token |
| `R2_SECRET_ACCESS_KEY` | المفتاح السري لنفس الـ Token (صلاحية Object Read & Write) |
| `R2_BUCKET_NAME` | اسم الـ Bucket |
| `R2_PUBLIC_BASE_URL` | رابط الوصول العام للـ Bucket (r2.dev أو دومين مخصص) بدون `/` في النهاية |

انسخ القيم إلى `backend/.env` (انظر الملف النموذجي `backend/.env.example`).

### 2) نقل الصور القديمة من قاعدة البيانات

```bash
cd backend
python manage.py migrate_base64_to_r2 --dry-run   # معاينة العدد والحجم فقط
python manage.py migrate_base64_to_r2             # النقل الفعلي (آمن للتكرار)
```

### 3) سلوك المعالجة

- أي صورة `<= 2MB` وأبعادها `<= 3200px` تُرفع كما هي بدون أي تعديل.
- الصور الأكبر تُضغط تلقائياً (جودة 92 → 88 → 85 ثم تصغير تدريجي) حتى تصل إلى 2MB أو أقل.
- أي محاولة لحفظ Base64 جديدة تُرفع تلقائياً إلى R2 وتُستبدل برابطها؛ وإذا لم تُضبط بيانات R2 يفشل الطلب
  بـ `400` / `503` بدلاً من تخزين Base64 في قاعدة البيانات.
- نقطة الرفع: `POST /api/upload-image/` (multipart: `file` + `folder`) وتعيد `{ url, key, size, content_type }`.
- اختبارات الوحدة: `python manage.py test api.tests_storage`.
